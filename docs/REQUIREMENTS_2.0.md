# CppDefense 2.0 — требования к продукту

**Статус:** базовая спецификация для разработки 2.0-alpha  
**Версия документа:** 1.4  
**Дата создания:** 2026-09-03  
**Последнее обновление:** 2026-09-11

**Связанный документ:** [План разработки CppDefense 2.0](DEVELOPMENT_PLAN_2.0.md)

Изменения 1.4: добавлены регистрация, вход и подтверждение личности через GitHub OAuth; Telegram оставлен альтернативным способом входа и дополнительной привязкой.  
Изменения 1.3: репозитории остаются публичными как портфолио, но код публикуется по проприетарной source-available лицензии, а не по open-source лицензии.  
Изменения 1.2: проект переведён на проприетарную модель; пользователи получают доступ к развёрнутому сервису, но не права использовать исходный код.  
Изменения 1.1: ручная проверка импорта, новая Telegram-привязка без GitHub OAuth, история компиляций для teacher/admin, admin view-as-role и требования к постоянному хранению.

## 1. Назначение

CppDefense 2.0 — локально разворачиваемая веб-система для проведения защит лабораторных работ по C++. Система принимает проекты студентов, выбирает функцию из их собственного кода, предлагает восстановить её тело за ограниченное время и проверяет результат через CMake, сборку и CTest в изолированном окружении.

Целевой масштаб одного развёртывания:

- до 100 одновременно зарегистрированных пользователей;
- 4–6 одновременно выполняющихся проверок;
- один преподаватель может вести несколько групп;
- один студент относится к одной учебной группе в рамках версии 2.0.

## 2. Границы версии 2.0

В версию 2.0 входят:

- регистрация и вход через GitHub OAuth;
- альтернативный вход и дополнительная привязка через Telegram OIDC;
- автоматическая или подтверждаемая преподавателем связь входа с записью студента;
- роли и разграничение доступа;
- группы, лабораторные работы, версии загруженного кода и защиты;
- импорт общего архива группы и отдельной лабораторной;
- предварительный просмотр импорта до записи изменений;
- хранение исходных и нормализованных ZIP-архивов;
- запуск и восстановление защиты после перезагрузки сайта;
- очередь проверок и отдельный runner;
- изолированная сборка CMake и запуск CTest;
- история попыток, результаты и технические логи;
- резервное копирование и базовый мониторинг;
- закрытая проприетарная лицензия и указание авторства владельца CppDefense.

В версию 2.0 не входят:

- самостоятельная регистрация преподавателей и администраторов;
- несколько организаций в одной установке;
- поддержка языков, отличных от C++;
- выполнение произвольных преподавательских скриптов вне утверждённого конвейера;
- совместное редактирование кода;
- чтение приватных репозиториев GitHub и загрузка лабораторных напрямую из GitHub;
- мобильное приложение;
- публичный доступ к загруженному коду студентов или учебным результатам.

## 3. Термины и сущности

- **Пользователь** — учётная запись со статусом, ролью и одной или несколькими внешними идентичностями GitHub/Telegram.
- **Запись студента** — созданная импортом или преподавателем запись с группой и GitHub login; до подтверждённого входа она не является активной учётной записью.
- **Студент** — пользователь, чья подтверждённая GitHub- или Telegram-идентичность связана с записью студента.
- **Преподаватель** — пользователь, управляющий назначенными ему группами и их работами.
- **Администратор** — пользователь, управляющий всеми пользователями, группами и настройками установки.
- **Группа** — учебная группа с уникальным стабильным кодом, например `iu7-21b`.
- **Лабораторная** — описание задания с уникальным в пределах группы кодом, например `lab-01`, и параметрами защиты.
- **Версия работы** — неизменяемый снимок проекта одного студента по одной лабораторной.
- **Импорт** — загрузка, проверка, предварительный просмотр и применение ZIP-архива.
- **Защита** — ограниченная по времени сессия восстановления выбранной функции.
- **Попытка проверки** — один снимок ответа, переданный в очередь.
- **Задание проверки** — техническая единица очереди, исполняемая runner-агентом.
- **Оригинальный архив** — загруженные байты ZIP без изменений.
- **Нормализованный архив** — безопасный архив ровно одного проекта после распаковки, фильтрации и повторной упаковки системой.

Все идентификаторы сущностей внутри системы — UUID. Время хранится в UTC, отображается в часовом поясе пользователя или установки.

## 4. Зафиксированные продуктовые решения

### 4.1 Frontend

Для 2.0 выбран **Go templates + HTMX** с небольшим количеством обычного JavaScript для редактора, таймера и отображения прогресса.

Причины выбора:

- интерфейс преимущественно состоит из форм, таблиц и экранов состояния;
- серверная проверка прав остаётся единой для HTML и API;
- меньше отдельной frontend-инфраструктуры и дублирования моделей;
- этого достаточно для расчётной нагрузки и первого полного релиза.

Backend при этом публикует версионированный REST API `/api/v1`; frontend не является единственным клиентом API. Переход на React/Vue в будущем не должен требовать изменения доменной модели.

### 4.2 Идентификация и привязка студента

GitHub OAuth является основным способом регистрации и входа студента. Авторитетным идентификатором после OAuth является неизменяемый числовой `github_user_id`; `github_login` используется в списках групп, ZIP manifest и интерфейсе, но может меняться.

Порядок создания и привязки:

1. Преподаватель загружает список группы или общий ZIP с GitHub login студентов.
2. Backend создаёт неподтверждённые записи студентов и привязывает к ним импортированные лабораторные.
3. Студент выбирает «Войти через GitHub» и подтверждает доступ к базовому профилю.
4. Backend получает проверенные `github_user_id` и `github_login`.
5. Если login совпал ровно с одной свободной записью студента, Backend автоматически связывает её с `github_user_id`, назначает роль `student` и статус `active`.
6. Если свободная запись не найдена или обнаружен конфликт, пользователь получает статус `pending`, а teacher своей группы или admin подтверждает связь вручную.
7. Пользователь получает доступ ко всем версиям лабораторных, уже связанным с этой записью.

`github_login` нормализуется приведением к нижнему регистру. После первой привязки личность определяется только по `github_user_id`; при смене login Backend обновляет отображаемое значение и пишет изменение в audit. Один GitHub ID и один Telegram `sub` могут принадлежать только одному пользователю, а одна запись студента — только одному активному пользователю.

### 4.3 Неизменяемость версий

Успешный повторный импорт никогда не перезаписывает существующую версию работы. Он создаёт новую версию с SHA-256 исходного и нормализованного архивов. Уже начатая защита всегда ссылается на конкретную версию и не меняется после нового импорта.

### 4.4 Таймер и очередь

Таймер защиты считается на сервере. Проверка, поставленная в очередь до крайнего срока, может завершиться после него и засчитывается по результату. После крайнего срока новые попытки не принимаются.

Для одной защиты одновременно допускается не более одной незавершённой попытки. Повторное нажатие кнопки проверки с тем же ключом идемпотентности не создаёт новое задание.

### 4.5 Просмотр интерфейса от лица роли

Admin может переключить режим интерфейса между `admin`, `teacher` и `student`, не меняя свою настоящую роль и повторно не входя через GitHub или Telegram.

- Переключатель меняет навигацию, страницы и доступные элементы управления.
- Для режима teacher выбирается группа, для режима student — запись студента.
- На каждой странице показывается заметная плашка режима просмотра и кнопка возврата в admin.
- Режим хранится в серверной сессии, не в базе как новая роль пользователя.
- По умолчанию режим только для чтения: действия, меняющие учебные данные или результаты, заблокированы.
- Полный тест изменяющих сценариев разрешён только на группе с признаком `demo`; все такие действия журналируются как выполненные администратором в режиме просмотра.
- Backend не доверяет присланному клиентом значению роли и проверяет, что настоящая роль пользователя — `admin`.

## 5. Роли и права

У активного пользователя ровно одна настоящая роль: `student`, `teacher` или `admin`. Пользователь в состоянии `pending` или `rejected` ещё не имеет рабочей роли. Заблокированный пользователь не может войти и выполнять действия независимо от роли.

| Возможность | Student | Teacher | Admin |
|---|---:|---:|---:|
| Просматривать свой профиль | Да | Да | Да |
| Зарегистрироваться/войти через GitHub | Да | Да, после назначения | Да, после назначения |
| Привязать дополнительный Telegram-вход | Да | Да | Да |
| Подтвердить спорную привязку студента | Нет | Да, в своей группе | Да |
| Видеть собственные работы и защиты | Да | Нет | Да |
| Начинать и проходить свою защиту | Да | Нет | Только на demo-данных в режиме student |
| Видеть состав назначенной группы | Нет | Да | Да |
| Видеть код студентов назначенной группы | Нет | Да | Да |
| Создавать лабораторные в назначенной группе | Нет | Да | Да |
| Загружать ZIP для назначенной группы | Нет | Да | Да |
| Проверять и подтверждать импорт | Нет | Да, в своей группе | Да |
| Видеть историю и итог компиляций | Только свои | Да, в своей группе | Да |
| Отменять активную защиту студента | Нет | Да, с причиной | Да, с причиной |
| Повторно открыть защиту | Нет | Да, с причиной | Да, с причиной |
| Управлять группами и назначением преподавателей | Нет | Нет | Да |
| Менять роли и блокировать пользователей | Нет | Нет | Да |
| Просматривать общесистемные логи и состояние runner | Нет | Нет | Да |
| Переключать режим отображения admin/teacher/student | Нет | Нет | Да |

Дополнительные правила:

- студент видит только собственные исходники, попытки, результаты и логи;
- преподаватель видит данные только назначенных ему групп;
- проверка доступа выполняется сервером на каждом HTML- и API-endpoint, а не только в интерфейсе;
- преподаватель не может незаметно изменить результат: отмена, повторное открытие и ручная корректировка сопровождаются причиной и записью аудита;
- admin имеет полный доступ, но каждое чтение архива и изменение результата журналируется.

## 6. Авторизация и учётные записи

### 6.1 Способы входа

- GitHub OAuth — основной способ регистрации и входа.
- Telegram OIDC — альтернативный способ входа и необязательная дополнительная привязка.
- Для доступа достаточно одной связанной идентичности; после привязки обеих пользователь входит в одну и ту же учётную запись любым способом.
- Backend создаёт собственную серверную сессию в cookie `HttpOnly`, `Secure`, `SameSite=Lax`; OAuth/OIDC-токен не используется как сессия сайта.
- Выход отзывает серверную сессию. Блокировка пользователя отзывает все его активные сессии независимо от провайдера.

### 6.2 GitHub OAuth

- Используется OAuth 2.0 Authorization Code Web Flow с PKCE `S256` и обязательным непредсказуемым `state`.
- Callback использует постоянный HTTPS-домен CppDefense через Cloudflare Tunnel и точный разрешённый URL без wildcard.
- Запрашивается только минимальный доступ к базовому профилю; права на репозитории и организации не запрашиваются.
- Backend обменивает временный `code`, получает профиль, сохраняет `github_user_id`, актуальный `github_login`, display name/avatar при наличии и время проверки.
- Access token после получения профиля не хранится, если он не нужен для других явно утверждённых функций.
- `github_user_id` уникален во всей системе и не может быть связан с двумя пользователями.
- При повторном входе поиск выполняется по `github_user_id`, а не по изменяемому login.
- Автоматическая привязка к записи студента разрешена только при единственном точном совпадении нормализованного login и отсутствии существующей связи.
- Несовпадение, дубликат или уже занятая запись переводят пользователя в `pending` без доступа к лабораторным и требуют решения teacher/admin.

### 6.3 Telegram OIDC и связывание провайдеров

- Telegram-поток проверяет `state`, `nonce`, issuer, audience, подпись и срок действия токенов.
- Telegram `sub` уникален и не может быть привязан к двум пользователям.
- Неизвестный пользователь, впервые вошедший только через Telegram, получает `pending`; teacher/admin вручную связывает его с записью студента.
- Уже вошедший пользователь может добавить второй способ входа только через новый полный OAuth/OIDC-поток с недавним подтверждением своей серверной сессии.
- Если добавляемая внешняя идентичность уже принадлежит другой учётной записи, автоматическое объединение запрещено; случай передаётся admin.
- Удаление последнего доступного способа входа запрещено.

### 6.4 Статусы пользователя и назначение ролей

- `pending` — вход выполнен, но связь с записью студента или служебная роль ещё не подтверждена;
- `active` — роль назначена, пользователь может работать в пределах своих прав;
- `rejected` — запрос на привязку отклонён с причиной;
- `blocked` — вход и любые действия запрещены администратором.

Pending-пользователь видит только состояние запроса, безопасные сведения своего профиля и кнопку выхода. При ручном подтверждении teacher/admin видит провайдера, проверенный GitHub login или Telegram display name, выбранную запись студента и группу. Роли teacher/admin назначает администратор; первый admin создаётся одноразовой bootstrap-настройкой с заранее указанным GitHub ID или Telegram `sub`.

## 7. ZIP-контракты

### 7.1 Общие правила

Оба формата используют ZIP и обязательный файл `cppdefense-manifest.json` в корне. Manifest кодируется UTF-8, имеет размер не более 1 MiB и соответствует JSON Schema версии формата.

Внутренние пути:

- относительные, с разделителем `/`;
- не начинаются с `/`, `\\` или буквы диска;
- не содержат пустых сегментов, `.` или `..`;
- не содержат управляющих символов;
- после Unicode-нормализации NFC должны оставаться уникальными;
- сравниваются без учёта регистра для обнаружения конфликтов с Windows.

Система отклоняет архив целиком, если обнаружены ZIP Slip, зашифрованная запись, символьная/жёсткая ссылка, специальный файл, несколько manifest-файлов, повреждённый ZIP или превышение лимита. Каталоги `.git`, `.svn`, `.idea`, `.vscode`, `build`, `cmake-build-*` и файлы результатов CppDefense не попадают в нормализованный архив; их наличие показывается как предупреждение.

Значения по умолчанию, изменяемые только администратором:

| Лимит | Архив группы | Отдельная лабораторная |
|---|---:|---:|
| Размер загруженного ZIP | 500 MiB | 100 MiB |
| Суммарный распакованный размер | 2 GiB | 300 MiB |
| Число файлов | 20 000 | 5 000 |
| Размер одного файла | 25 MiB | 25 MiB |
| Глубина пути | 20 | 20 |
| Максимальный коэффициент распаковки | 100:1 | 100:1 |

Для проекта обязательны корневой `CMakeLists.txt` и хотя бы один файл `.c`, `.cc`, `.cpp`, `.cxx`, `.h`, `.hh`, `.hpp` или `.hxx`. Пустые проекты и вложенные ZIP не импортируются.

### 7.2 Общий архив группы

Один архив содержит одну группу и одну или несколько работ разных студентов. Пути проектов задаются manifest-файлом; рекомендуемая физическая структура показана ниже, но система не извлекает идентичность из имени каталога.

```text
group.zip
├── cppdefense-manifest.json
└── projects/
    ├── ivanov/lab-01/...
    ├── ivanov/lab-02/...
    └── petrova/lab-01/...
```

Минимальный manifest:

```json
{
  "schema_version": 1,
  "kind": "group",
  "group_code": "iu7-21b",
  "items": [
    {
      "lab_code": "lab-01",
      "student": {
        "github_login": "ivanov"
      },
      "project_path": "projects/ivanov/lab-01"
    }
  ]
}
```

Для каждого `items[]`:

- обязательны `lab_code`, `student` и `project_path`;
- `student` содержит обязательный `github_login`; другие идентификаторы GitHub не принимаются;
- пара «студент + лабораторная» встречается в архиве не более одного раза;
- `project_path` указывает на каталог, существует и не пересекается с путём другого элемента;
- группа и лабораторная уже существуют в системе;
- существующая запись студента состоит в указанной группе; если записи ещё нет, она создаётся в этой группе со статусом `unclaimed`.

### 7.3 Архив отдельной лабораторной

Один архив содержит ровно один проект одного студента по одной лабораторной.

```text
lab.zip
├── cppdefense-manifest.json
└── project/
    ├── CMakeLists.txt
    └── ...
```

Минимальный manifest:

```json
{
  "schema_version": 1,
  "kind": "lab",
  "group_code": "iu7-21b",
  "lab_code": "lab-01",
  "student": {
    "github_login": "ivanov"
  },
  "project_path": "project"
}
```

Правила идентификации, существования группы/лабораторной и состава проекта совпадают с форматом общего архива.

### 7.4 Предварительный просмотр, ручная проверка и применение

После автоматической валидации преподаватель или администратор обязан вручную проверить preview. Reviewer видит:

- SHA-256 и размер исходного архива;
- группу и список распознанных элементов;
- найденного студента и лабораторную для каждого элемента;
- число файлов и распакованный размер;
- действие `create_student_and_version`, `create_version`, `skip_duplicate` или `conflict`;
- ошибки и предупреждения с путём к проблемному элементу.

Совпадение SHA-256 нормализованного проекта с последней версией даёт `skip_duplicate`. Новый корректный GitHub login в group ZIP даёт `create_student_and_version`. GitHub login, уже занятый записью другой группы, неизвестная лабораторная, неоднозначное сопоставление и пересечение путей дают `conflict`.

Reviewer подтверждает чек-лист: выбрана верная группа, студенты сопоставлены верно, лабораторные распознаны, размеры ожидаемы, ошибки отсутствуют. Подтверждать импорт может teacher своей группы либо admin; загрузивший архив пользователь вправе проверить его сам. Двойное согласование для 2.0 не требуется.

Применение импорта возможно только после ручного подтверждения. Для 2.0 действует атомарный режим: если хотя бы один элемент имеет ошибку или конфликт, подтверждение и применение недоступны; предупреждения не блокируют подтверждение. Backend сохраняет reviewer, UTC-время, результат чек-листа и SHA-256 проверенного архива. Если архив изменился, прежнее подтверждение аннулируется. Повторный запрос применения с тем же ключом идемпотентности не создаёт дубликаты.

## 8. Состояния

### 8.1 Загрузка и импорт

| Состояние | Значение | Допустимые следующие состояния |
|---|---|---|
| `receiving` | Backend принимает байты | `stored`, `rejected`, `cancelled` |
| `stored` | Исходный ZIP сохранён в MinIO | `validating`, `cancelled` |
| `validating` | Проверяются manifest, лимиты и проекты | `review_pending`, `rejected`, `failed`, `cancelled` |
| `review_pending` | Preview готов и ожидает ручной проверки teacher/admin | `approved`, `rejected`, `cancelled` |
| `approved` | Reviewer подтвердил неизменившийся архив | `applying`, `cancelled` |
| `applying` | Создаются нормализованные архивы и версии | `completed`, `failed` |
| `completed` | Все версии созданы или отмечены дубликатами | — |
| `rejected` | Входные данные нарушают контракт либо reviewer отклонил импорт | — |
| `failed` | Внутренняя/инфраструктурная ошибка | `validating` или `applying` после ручного retry |
| `cancelled` | Импорт отменён пользователем | — |

Состояния `completed`, `rejected` и `cancelled` терминальные. Ошибка в пользовательском ZIP или ручное отклонение — `rejected`; недоступность MinIO или внутренняя ошибка — `failed`.

### 8.2 Защита

| Состояние | Значение | Допустимые следующие состояния |
|---|---|---|
| `ready` | Защита создана, но таймер не запущен | `preparing`, `cancelled` |
| `preparing` | C++-ядро анализирует проект и выбирает функцию | `active`, `error`, `cancelled` |
| `active` | Функция выбрана, таймер идёт, ответы принимаются | `passed`, `failed`, `expired`, `cancelled`, `error` |
| `passed` | Одна из допустимых попыток прошла сборку и тесты | — |
| `failed` | Студент завершил защиту без успеха либо преподаватель закрыл её | — |
| `expired` | Срок истёк и ни одна принятая вовремя попытка не прошла | — |
| `cancelled` | Защита отменена с указанием причины | — |
| `error` | Продолжение невозможно из-за системной ошибки | `ready` после ручного восстановления |

Для одного студента и одной версии работы допускается не более одной защиты в состояниях `ready`, `preparing` или `active`. Повторное открытие создаёт новую защиту, связанную с предыдущей, и требует причины.

Система сохраняет для защиты:

- версию работы и `session_id`;
- список top-N кандидатов и выбранную функцию;
- исходное тело, сигнатуру, файл и диапазон строк;
- время создания, начала и серверный deadline;
- текущий черновик ответа;
- все попытки и итог;
- причину отмены, ошибки или повторного открытия.

### 8.3 Задание проверки

| Состояние | Значение | Допустимые следующие состояния |
|---|---|---|
| `queued` | Задание ожидает runner | `leased`, `cancelled` |
| `leased` | Runner получил аренду задания | `running`, `queued`, `cancelled` |
| `running` | Контейнер выполняет CMake → Build → CTest | `completed`, `retry_wait`, `timed_out`, `cancelled` |
| `retry_wait` | Инфраструктурная ошибка, ожидается повтор | `queued`, `dead` |
| `completed` | Конвейер завершён с доменным итогом `passed` или `failed` | — |
| `timed_out` | Превышен лимит выполнения | — |
| `cancelled` | Задание отменено до завершения | — |
| `dead` | Исчерпаны повторы инфраструктурной ошибки | — |

Ошибки компиляции и упавшие тесты дают `completed` + outcome `failed` и не повторяются автоматически. Потеря runner, сбой контейнерного runtime или временная недоступность хранилища являются инфраструктурными ошибками и могут повторяться. Аренда задания продлевается heartbeat; после её истечения задание возвращается в очередь, если лимит повторов не исчерпан.

## 9. Функциональные требования

### 9.1 Группы и лабораторные

- Admin создаёт, архивирует и переименовывает группы, назначает им преподавателей и студентов.
- Teacher или admin загружает список студентов с GitHub login либо создаёт запись студента вручную.
- Teacher своей группы и admin видят pending GitHub/Telegram-пользователей и могут подтвердить их связь со свободной записью студента.
- Код группы стабилен и уникален; отображаемое название можно менять.
- Teacher создаёт лабораторную только в своей группе.
- Лабораторная содержит код, название, описание, активность, лимит времени, число кандидатов для случайного выбора и параметры проверки.
- Значения по умолчанию: 10 минут, top-5 функций, CMake configure/build и CTest.
- Архивирование группы или лабораторной запрещает новые импорты и защиты, но сохраняет историю.

### 9.2 Работа студента

- После GitHub-входа и автоматической либо ручной привязки студент видит только лабораторные своей записи, последнюю версию и историю защит.
- Перед запуском показываются правила, лимит времени и явное подтверждение старта.
- После старта студент видит путь, сигнатуру и контекст выбранной функции, но не исходное тело.
- Редактор изменяет только ответ для выбранного тела функции; загруженный архив неизменяем.
- Черновик сохраняется автоматически и восстанавливается после перезагрузки страницы.
- Студент видит серверное оставшееся время, место в очереди как приблизительное значение, состояние проверки и безопасно отфильтрованный лог.
- При неуспешной попытке активная защита продолжается, если deadline ещё не наступил.
- После терминального состояния редактирование и новые проверки запрещены.

### 9.3 C++-ядро и worker

- Существующий CLI сохраняется как отдельный интерфейс к `cpp-defense-core`.
- `cpp-defense-worker` работает без интерактивного терминала и принимает/возвращает версионированный JSON.
- Операции worker включают как минимум анализ проекта, подготовку защиты и формирование проекта с ответом для проверки.
- Каждый вызов использует уникальный `session_id`; общий изменяемый каталог `cache/current` запрещён.
- Одинаковые входные данные и seed выбора дают одинаковый список кандидатов и выбранную функцию.
- Ошибки worker возвращаются структурированно: код, безопасное сообщение и диагностические детали для внутреннего лога.
- Ни worker, ни runner не изменяют оригинальный или нормализованный архив в MinIO.

### 9.4 Проверка

- Runner получает задания только через аутентифицированный служебный интерфейс.
- Каждая попытка выполняется в новом контейнере без сети и без доступа к данным других попыток.
- Этапы выполняются последовательно: распаковка нормализованного проекта, подстановка ответа, CMake configure, build, CTest.
- Успех означает нулевые коды завершения всех обязательных этапов и успешное завершение CTest.
- Лимиты CPU, RAM, PID, диска, времени и размера логов задаются конфигурацией и фиксируются в результате попытки.
- Контейнер работает непривилегированным пользователем, с read-only системным образом и записываемым одноразовым workspace.
- Workspace полностью удаляется после результата, ошибки или таймаута.
- Секреты, токены и сетевые учётные данные не передаются в контейнер.

### 9.5 История и аудит

- Пользовательский результат содержит функцию, число попыток, длительность, время завершения и итог.
- Для каждой попытки сохраняются ответ, этапы, exit codes, ограниченный stdout/stderr, время, runner и версия образа.
- Teacher видит по студентам своих групп список всех попыток компиляции: лабораторную, версию работы, номер попытки, время постановки/начала/завершения, состояние очереди, итог configure/build/CTest, exit codes и очищенный лог.
- Admin видит ту же историю для всех групп, а также runner, версию worker/контейнерного образа, инфраструктурные повторы и причины `timed_out`/`dead`.
- На уровне защиты teacher/admin видит сводный итог: `passed`, `failed`, `expired`, `cancelled` или `error`, число попыток, длительность и успешную попытку.
- Историю можно фильтровать по группе, студенту, лабораторной, периоду и итогу; экспорт CSV не содержит исходный код или полный ответ студента.
- Результат попытки после сохранения неизменяем. Ручная корректировка создаёт отдельную запись решения с автором и причиной, не переписывая технический результат.
- Аудит неизменяемо фиксирует входы, создание и удаление GitHub/Telegram-привязок, подтверждения/отклонения спорных связей, смену ролей/блокировку, проверки и применение импортов, чтение архивов, создание/отмену/повторное открытие защит, режим просмотра роли и ручные изменения результата.
- В audit entry входят actor, действие, объект, UTC-время, request ID и причина, если она обязательна.

## 10. Данные и хранение

PostgreSQL является источником истины для метаданных и состояний. MinIO хранит:

- оригинальные загруженные ZIP;
- нормализованные архивы отдельных проектов;
- большие технические логи, если они превышают лимит хранения в PostgreSQL.

Все MinIO-объекты приватны. Backend выдаёт короткоживущие ссылки только после повторной проверки прав либо проксирует скачивание. Object key не содержит Telegram ID, GitHub login, ФИО или другие персональные данные.

Минимальные связи данных:

- user ↔ telegram_identity (0..1:1);
- user ↔ github_identity (0..1:1);
- user ↔ student_record (0..1:0..1);
- github_identity содержит уникальный `github_user_id`, актуальный login и время последней проверки; долгоживущий OAuth-токен не хранится;
- student_record содержит нормализованный GitHub login для сопоставления с импортом и после привязки ссылается на user;
- group ↔ teacher (M:N);
- group ↔ student_record (1:N для 2.0);
- group → lab (1:N);
- lab + student → submission_version (1:N);
- submission_version → defense (1:N);
- defense → check_attempt (1:N);
- check_attempt → check_job (1:1, с историей аренды/повторов отдельно);
- import → import_item (1:N).

Удаление пользователя по умолчанию логическое. Учебные результаты и audit не удаляются каскадно. Политика окончательного удаления оформляется отдельной административной процедурой.

## 11. Нефункциональные требования

### 11.1 Производительность и надёжность

- Система поддерживает 100 одновременно активных пользовательских сессий без потери данных.
- Публичный HTTPS-домен, страница входа и GitHub OAuth callback доступны напрямую через Cloudflare Tunnel и не требуют подключения пользователя к домашней сети или VPN.
- Полный сценарий GitHub-входа и работы студента не делает клиентских запросов к Telegram.
- Перед выпуском доступность домена CppDefense и GitHub OAuth проверяется из целевых сетей студентов; приложение показывает понятную ошибку при недоступности внешнего провайдера.
- Число параллельных контейнеров настраивается; штатное значение — от 4 до 6.
- P95 ответа обычного HTML/API endpoint — не более 500 мс без учёта загрузки файла и фоновых операций.
- После перезапуска Backend незавершённые импорты и задания либо продолжаются, либо переходят в явное восстанавливаемое состояние.
- Потеря heartbeat не должна приводить к одновременному исполнению одного задания двумя runner; завершение принимается только владельцем актуальной аренды.
- Все команды, создающие сущности или задания, поддерживают идемпотентность.

### 11.2 Безопасность

- TLS завершается через Cloudflare Tunnel; прямой публичный доступ к VM закрыт.
- CSRF-защита обязательна для изменяющих запросов с cookie-сессией.
- На начало входа, OAuth/OIDC callback, создание pending-запроса, загрузку, создание защиты и постановку проверки действуют rate limits.
- OAuth/OIDC client secrets хранятся вне репозитория и не передаются frontend или runner.
- SQL строится параметризованно; HTML экранируется по умолчанию.
- Логи не содержат токенов, session cookie, полного содержимого исходников и ответа студента.
- Пользовательский build-log очищается от абсолютных путей хоста и инфраструктурных секретов.
- Зависимости и контейнерный образ сканируются; критические уязвимости блокируют выпуск.

### 11.3 Резервное копирование и восстановление

- Перезапуск или штатное выключение Windows, обеих VM, Backend, PostgreSQL либо MinIO не приводит к потере подтверждённых данных.
- Каталоги данных PostgreSQL и MinIO размещаются на постоянных виртуальных дисках VM, а не во временной файловой системе контейнера. При контейнерном запуске используются явно подключённые persistent volumes.
- Очередь хранится в PostgreSQL; после запуска незавершённые задания восстанавливаются по состоянию и сроку аренды.
- Конфигурация развёртывания, миграции и сведения о версиях образов сохраняются вместе с резервной копией, но секреты хранятся отдельно в зашифрованном виде.
- PostgreSQL ежедневно сохраняется согласованным `pg_dump`; объекты MinIO ежедневно копируются с проверкой контрольных сумм.
- Минимум одна копия PostgreSQL и MinIO хранится **вне диска домашнего ноутбука**: на отключаемом внешнем диске, NAS или в зашифрованном облачном хранилище. Резервная копия только во второй VM на том же физическом диске недостаточна.
- Хранятся минимум 7 ежедневных и 4 еженедельных комплектов резервных копий.
- Цели для 2.0: RPO не более 24 часов, RTO не более 4 часов.
- После каждого backup-задача проверяет успешное завершение, размер и контрольные суммы; ошибка отображается admin и создаёт оповещение.
- Не реже одного раза перед релизом и затем ежемесячно выполняется документированная проверка восстановления PostgreSQL и MinIO на чистом окружении.

### 11.5 Наблюдаемость

- Метрики: свободное место, RAM/CPU VM, доступность PostgreSQL/MinIO, длина и возраст очереди, активные runner, heartbeat, длительность и исходы проверок, число ошибок импорта.
- Коррелируемый request/job/session ID присутствует во внутренних логах.
- Admin видит состояние runner и очередь без доступа к shell VM.

### 11.6 Совместимость и доступность

- Поддерживаются актуальные стабильные версии Chrome, Edge и Firefox на desktop.
- Основные сценарии доступны с клавиатуры; элементы форм имеют подписи, состояния не передаются только цветом.
- Пользовательский интерфейс и сообщения об ошибках версии 2.0 — на русском языке; машинные коды ошибок — стабильные английские идентификаторы.

## 12. Сквозные сценарии приёмки

### A. Успешная защита

1. Student входит через GitHub; проверенный GitHub ID связан с его записью студента.
2. Видит импортированную версию своей лабораторной и подтверждает старт.
3. Система выбирает функцию и запускает серверный таймер.
4. Student вводит тело функции и ставит проверку в очередь.
5. Runner выполняет CMake, build и CTest в новом контейнере.
6. Все этапы успешны; попытка получает outcome `passed`, защита — `passed`.
7. После обновления страницы доступны тот же итог и история попытки.

### B. Ошибка компиляции с повтором

1. Попытка принята до deadline и завершается ошибкой компиляции.
2. Job имеет состояние `completed`, outcome `failed`; автоматического retry нет.
3. Student видит очищенный лог, исправляет ответ и запускает новую попытку до deadline.
4. Предыдущая попытка остаётся в истории.

### C. Очередь около deadline

1. Student отправляет попытку до deadline, но свободного runner нет.
2. После deadline новые попытки запрещены, уже поставленная остаётся допустимой.
3. Если отложенная попытка проходит, защита получает `passed`; иначе после её завершения — `expired`.

### D. Импорт группы

1. Teacher загружает корректный group ZIP для назначенной группы.
2. Система не создаёт версии до автоматической проверки и ручного подтверждения.
3. Preview показывает сопоставления, размеры, SHA-256, действия и предупреждения.
4. Teacher или admin проверяет чек-лист и подтверждает неизменившийся архив.
5. После подтверждения все элементы атомарно создают новые версии или пропускаются как точные дубликаты.
6. Reviewer, время и SHA-256 сохраняются в аудите.
7. Student видит только собственные новые версии.

### E. Небезопасный архив

1. ZIP содержит путь `../../...`, ссылку или превышает лимит распаковки.
2. Импорт получает `rejected`, ни один проект не записывается как версия.
3. Teacher получает безопасное сообщение с причиной; попытка фиксируется в audit.

### F. Сбой runner

1. Runner теряет heartbeat во время инфраструктурного сбоя.
2. После истечения аренды задание возвращается в очередь и получает новый номер попытки исполнения.
3. Старый runner не может записать результат по просроченной аренде.
4. Для студента не создаётся дополнительная попытка защиты.

### G. Проверка разграничения доступа

1. Student A запрашивает URL/API объекта Student B и получает отказ без утечки существования/содержимого.
2. Teacher группы A не может получить архив группы B.
3. Admin может получить объект, а доступ появляется в audit.

### H. Первичная регистрация через GitHub

1. Общий ZIP создаёт запись студента `ivanov` и связывает с ней лабораторные.
2. Владелец GitHub-аккаунта `ivanov` проходит OAuth.
3. Backend получает числовой GitHub ID, находит единственную свободную запись `ivanov` и автоматически связывает её.
4. Система активирует роль student и открывает лабораторные этой записи без участия Telegram.
5. Если совпадения нет или запись занята, пользователь остаётся `pending`, а teacher/admin принимает решение вручную.
6. Попытка связать тот же GitHub ID или ту же запись повторно отклоняется и попадает в audit.

### I. История компиляций

1. Teacher открывает студента своей группы и видит все его попытки с итогами configure/build/CTest.
2. Teacher открывает очищенный лог конкретной попытки и сводный итог защиты.
3. Попытка доступа к истории чужой группы отклоняется.
4. Admin видит те же данные по всем группам и дополнительные инфраструктурные сведения runner.

### J. Режим просмотра роли

1. Admin выбирает режим student и конкретную тестовую запись.
2. Интерфейс показывает student-навигацию и постоянную плашку режима просмотра.
3. Изменение реальных учебных данных заблокировано; в demo-группе тестовые действия разрешены и записываются от имени admin.
4. Возврат в admin не требует повторного входа через GitHub/Telegram и не меняет роль в базе.

### K. Выключение и восстановление

1. После штатного выключения ноутбука запускаются обе VM, PostgreSQL, MinIO, Backend и runner.
2. Пользователи, группы, лабораторные, архивы, защиты и история попыток доступны без ручного импорта.
3. Просроченная аренда незавершённого job корректно возвращается в очередь.
4. Отдельная проверка восстановления из внешней резервной копии возвращает согласованные записи PostgreSQL и соответствующие им MinIO-объекты.

## 13. Условия завершения этапа «Зафиксировать требования»

Этап считается завершённым, когда команда принимает этот документ как baseline и дальнейшие изменения проходят через versioned change record. Перед реализацией соответствующего модуля должны быть дополнительно созданы:

- JSON Schema для двух manifest-форматов;
- OpenAPI-контракты на основе состояний и прав из этого документа;
- JSON Schema протокола `cpp-defense-worker`;
- модель угроз sandbox и импорта;
- ER-диаграмма и миграционный план PostgreSQL.

Эти артефакты относятся к этапам 2, 3, 6 и 8 и не блокируют фиксацию продуктовых требований.

## 14. Допущения baseline

Следующие положения считаются принятыми для 2.0 и меняются только явным решением:

- архив отдельной лабораторной означает один проект одного студента;
- общий архив относится ровно к одной группе;
- частичное применение общего архива не поддерживается;
- импорт требует одного ручного подтверждения teacher своей группы или admin; подтверждение вторым человеком не требуется;
- студент состоит только в одной активной группе;
- GitHub OAuth является основным способом регистрации и входа, Telegram OIDC — альтернативным и необязательным;
- GitHub login используется для первичного сопоставления, после которого постоянной внешней идентичностью становится числовой GitHub ID;
- при единственном свободном совпадении GitHub login студент активируется автоматически, иначе остаётся `pending` до ручного решения;
- admin переключает режим представления интерфейса без реальной смены роли;
- одна незавершённая проверка на защиту;
- попытка, принятая до deadline, засчитывается после deadline;
- manifest обязателен, эвристический импорт по названиям папок отсутствует;
- CTest обязателен для успешной защиты;
- frontend реализуется на Go templates + HTMX;
- все репозитории публичны для просмотра как портфолио, но это не даёт разрешения использовать код в других проектах;
- CppDefense использует проприетарную source-available лицензию, не MIT и не другую open-source лицензию;
- права на сторонние компоненты и работы студентов не присваиваются.
