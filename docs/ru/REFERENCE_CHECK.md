# Быстрый зачёт по проверенному оригиналу

Проверка выполняется доверенным runner на сервере. Браузер отправляет только
ответ, не признак «правильно». Оригинальный фрагмент не передаётся студенту.

## Порядок проверки

1. При финальной подготовке восстановления runner проверяет неизменённый
   оригинал: CMake, сборка и CTest. В «Прятках» эта проверка уже входит в
   подготовку; сохраняется также результат проверки возвращённого оригинала.
2. При отправке восстановления сравнивается **тело выбранной сущности**
   (функции, класса или структуры) с оригиналом. Проверяется и SHA исходного
   файла, и границы тела.
3. В «Прятках» сначала собирается итоговая карта исходников и заголовков:
   оригинал + изменения преподавателя + правки студента. Все редактируемые
   файлы должны совпасть с оригиналом, не только выбранные преподавателем.
   Защита тестов, CMake и зависимостей остаётся прежней.
4. При совпадении с успешно проверенным оригиналом попытка получает
   `passed` и защита заканчивается по обычному правилу, без новой сборки.
5. При отличии выполняются прежние материализация, сборка и тесты.
   Другой правильный алгоритм не отклоняется из-за несовпадения с эталоном.

Нормализуются **только CRLF → LF**. Пробелы, комментарии, отступы и строки
сравниваются точно. Совпадение хеша не используется как замена сравнению
ответа; хеши связывают результат предварительной проверки с контекстом.
CTest запускается с `--no-tests=error`: работа без зарегистрированных тестов
не считается проверенным эталоном и не проходит обычную проверку автоматически.

## Когда результат оригинала можно повторно использовать

Приватный кэш runner привязан к:

- неизменяемому ключу версии работы и сессии защиты;
- SHA-256 содержимого **всех** файлов проекта, включая CMake, тесты и входные
  данные, а также структуре каталогов;
- фактическому immutable image ID, полученному через container image inspect,
  а не изменяемому тегу; предварительная проверка выполняется по этому ID;
- фактическим аргументам sandbox, скрипту CMake/build/CTest, runtime и лимиту
  времени проверки.

Без дискового снимка подтверждения находятся в памяти runner до одного часа
и ограничены 256 записями. Проверенный дисковый снимок сохраняет подтверждение
между перезапусками; по истечении срока подтверждения оригинал проверяется
заново в отдельной рабочей копии. Изменение версии, образа или настроек
инвалидирует снимок. Подробности: [инкрементальные сборки](INCREMENTAL_BUILDS.md).
Если immutable ID образа определить нельзя, быстрый зачёт отключён:
используется обычная сборка и тестирование ответа.

Кэшируются успешные результаты только оригинальной версии, не ответы
студентов. Ошибка или таймаут не создаёт подтверждения. Постоянный ccache
доступен только сборке оригинала; попытки студентов его не изменяют.

## Что видно в результате

Студент, преподаватель и администратор видят:
«Ответ совпал с проверенным оригиналом — защита успешно сдана».
Отдельно указано, что повторная сборка и тесты **не запускались**.
В истории сохраняется `reference_result`: хеш проекта, immutable ID образа,
хеш политики и время первоначальной успешной проверки. Поля
`configure_result`, `build_result` и `ctest_result` остаются SQL NULL.
Они не подменяются фиктивными отметками OK.

## Развёртывание

Нужно обновить backend и Go runner через обычный GitHub deployment из одной
ветки; frontend встроен в backend. Миграция `000014_verified_reference.sql`
применяется стандартным механизмом. C++ worker и его протокол не меняются.
Новых секретов, пакетов или настроек VPS не требуется.

При первом запуске после обновления подготовка восстановления может занять
дольше прежнего: теперь оригинал действительно проходит тесты до старта
таймера. Сам импорт ZIP не является подтверждением успешных серверных тестов.
