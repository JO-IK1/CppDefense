# Доставка готового sandbox вместо сборки на VPS

GitHub Actions собирает `linux/amd64` sandbox и проверяет инкрементальные
сборки реальными Docker-контейнерами. Затем сохраняет образ через `docker save`
и gzip, проверяет загрузку архива в Podman на CI и передаёт три файла по SCP:
архив, его SHA-256 и immutable image ID. Ни PAT, ни registry credentials не нужны.

Только после успешных проверок и передачи начинается обновление приложения.
SSH/SCP используют ServerAliveInterval=15 и ServerAliveCountMax=12. Это помогает
обнаруживать потерю соединения, но не делает деплой независимым от сети.
Текущий production — x86_64; перенос на ARM требует отдельной смены платформы.

Root-установщик сериализован через flock. Он копирует загрузку в приватный
staging-каталог с root-owned родителем `/var/lib/cppdefense-releases`, проверяет
контрольную сумму и загружает образ именно в хранилище пользователя
`cppdefense-runner`, а не root. Проверяются ID, ОС/архитектура и запуск Ninja/GTest
без сети. Затем переключается прежний production-тег и обновляются бинарники.
При неуспешном запуске службы восстанавливаются предыдущие бинарники и тег.
Ошибки до переключения не меняют production-тег. Старые образы не удаляются.
Staging-файлы очищаются trap; после успешного/неуспешного deploy-app загрузка
удаляется. SIGKILL/потеря питания могут оставить файлы; очистка образов и диска
не выполняется автоматически.

SHA-256 защищает от повреждения передачи, не заменяет подпись издателя.
Доверие остаётся основанным на защищённой ветке, GitHub Actions, SSH-ключе и
проверенных host keys. Их проверки не отключены. Контроль актуальности root-копии
установщика также сохранён: workflow не получает новые sudo-права.

## Разовое обновление root-установщика

После merge новая версия попадёт в `/opt/cppdefense/source`, первый deploy
остановится с `runner installer on the VPS is outdated` до изменения backend.
Выполните на VPS:

```bash
sudo install -o root -g root -m 0755 \
  /opt/cppdefense/source/deploy/install-runner-release.sh \
  /usr/local/sbin/cppdefense-install-runner
```

Затем Re-run failed jobs в этом запуске GitHub Actions. Повторный запуск
повторно отправит архив. Не запускайте старую команду `deploy-app.sh` без загрузки
образа. Новая версия намеренно не откатывается к сетевой сборке на VPS.

## Проверки

```bash
python3 -m unittest discover -s deploy/tests -v
sh -n deploy/deploy-app.sh deploy/install-runner-release.sh
```

Тесты запускают настоящий shell-установщик с изолированными путями и имитацией
системных служб: успешный импорт, повреждённый архив, неверный ID, ошибка smoke
и откат при сбое restart. Workflow дополнительно проверяет реальный Docker
образ и реальную совместимость Docker archive → Podman. Проверка на VPS после
установки идёт через его rootless Podman. Состояние running через 2 секунды —
базовая проверка запуска службы, не доказательство прохождения всех лабораторных.
