# Загрузка задания и фоновый прогрев

## Отображение у студента

Исправлены независимые случаи пустого рабочего пространства:

- `repositoryLoaded` выставляется только после списка файлов **и первого файла**.
  Ошибка первого открытия больше не запрещает повторную загрузку при polling.
- Подготовка сигнатуры и исходников не зависит от анимации колеса. При отсутствии
  Web Animations API или ошибке анимации остаётся статический выбранный сектор.
- Таймер обновляется до запросов файлов; ошибка файлов не замораживает его.
  Отправка и сохранение ответа включаются только при полученном задании и файлах.
- Если API вернул active без challenge, показывается пояснение, а не пустой
  экран с разрешённой слепой отправкой. Polling продолжает повторные попытки.
- При начале новой защиты сбрасываются предыдущие файлы. Ответы старого запроса
  не должны перерисовывать уже другую выбранную защиту.

На сервере защита исходников режима «Прятки» ранее оставалась навсегда при
наличии **любого** исторического hide_seek на версии работы. Это убирало
challenge даже у следующего восстановления с активным таймером. Теперь охрана
действует, пока hide_seek находится в ready/preparing/active. После терминального
состояния прошлая задача не блокирует другую защиту на той же версии. Во время
незавершённых «Пряток» архивы и старые просмотры восстановления по-прежнему
недоступны студенту; полномочия преподавателя не меняются. Это не антиплагиат:
студент мог знать собственный исходный проект ещё до загрузки на сайт.

## Когда прогревается сборка

После **подтверждения и применения импорта**, а не непроверенной загрузки ZIP,
создаётся `runner_jobs.kind=warm_submission`. Одна работа — одно задание,
повторный импорт того же содержимого не дублирует прогрев. Старые загруженные
версии получают прогрев при первом начале защиты: анализ идёт первым, затем
прогрев может выполняться, пока преподаватель выбирает функцию.

Runner распаковывает исходники, создаёт проверенный снимок Ninja, запускает
CTest в отдельной копии и сохраняет только успешный baseline. Студенческие
изменения и состояние, оставленное тестами, обратно не публикуются.

Задание имеет приоритет -100, обычные защиты — 0 и выше. Heartbeat прогрева
каждые 5 секунд проверяет интерактивную очередь. При появлении обычной работы
lease прогрева возвращается в queued, старый token становится недействителен,
runner отменяет контейнер и берёт интерактивное задание. Прерывание — не ошибка
работы студента. Повторный прогрев ждёт свободного runner; cleanup может занять
дополнительное время. Провал прогрева не отменяет импорт и не выставляет оценку.
Таймеры защит от прогрева не запускаются.

Сохраняются версия работы, содержимое всех файлов, образ и настройки в ключе
кэша. Сессия больше не входит в ключ. Разные версии не делят снимок даже при
совпадающем исходнике. TTL/целостность/срок подтверждения по-прежнему проверяются.
Необходимые зависимости уже находятся в sandbox; сетевые загрузки внутри
студенческой сборки не разрешаются.

Прогрев не гарантирует мгновенного старта: остаются анализ, выбор преподавателя,
материализация, получение файлов браузером и очереди. Если снимок не готов,
удалён, устарел или сменился образ, обычная проверка оригинала выполняется при
подготовке защиты. Срок свежести подтверждения остаётся один час.

## Развёртывание и диагностика

Применяется вся серия коммитов, backend и runner обновляются вместе обычным
GitHub deployment. Миграции 000017/000018 добавляют тип фонового задания.
Старые runner не получают их без явного `accept_warmups=true`. Новых секретов,
root-установщика и ручных изменений VPS не требуется. При откате на старый
backend сначала остановите новый runner и завершите/отмените его фоновые lease:
старые backend не понимают новый тип задания с пустым defense_id.

Состояние прогрева можно посмотреть в БД (права преподавателя не расширяются):

```sql
select id, submission_version_id, state, retry_count, preparation_result
from runner_jobs where kind='warm_submission' order by created_at desc;
```

Для повторного исследования пустого задания нужны поля GET защиты challenge,
defense_mode, status, preparation_error, wheel_candidates и статус запросов
repository/file. Не публикуйте cookie, токены или приватный исходный архив.

Проверки: миграции и жизненный цикл на PostgreSQL, 18 тестов UI, реальные Linux
контейнеры с полным путём ZIP → warmup → снимок → другая сессия, а также проверки
изоляции и инвалидирования версии/образа/настроек. На production автоматически
ничего не менялось при подготовке патча.
