# Замеры и изолированные инкрементальные сборки

Основа изменений — main 90e6565. Это развитие существующего runner, не переход
на внешний сервис онлайн-компиляции. Применять нужно всю серию коммитов.

## Подготовка оригинала

Runner вычисляет ключ из неизменяемой версии/сессии, содержимого и структуры
проекта, immutable ID образа, фактических аргументов и скрипта sandbox,
лимита времени, версии формата снимка и настроек runtime. CMake-файлы,
тесты, данные и зависимости входят в хеш проекта.

1. Оригинал настраивается через CMake + Ninja и собирается в ограниченном
   приватном tmpfs `/build`.
2. **До CTest** содержимое сборки экспортируется через stdout в tar.
   Каталоги host-файловой системы не монтируются контейнеру на запись.
3. Runner проверяет архив: пути, типы файлов, ссылки, размеры, время и лимит
   числа файлов. Владельцы, устройства и host hard links не сохраняются.
4. Кандидат в снимок подключается только для чтения как `/seed` к новому
   контейнеру. Он копирует данные в свой пустой `/build` и запускает CTest.
5. Только при успешных тестах предтестовый снимок атомарно публикуется в кэш.
   Состояние, созданное тестами, не возвращается в снимок.

Оригинал проверяется до запуска таймера защиты. В «Прятках» дополнительно
проверяются испорченная и восстановленная версии, как раньше.

## Каждая попытка

- Исходники материализуются в отдельной временной папке; студент может менять
  только разрешённую часть проекта.
- Снимок проверяется по контексту, метаданным и SHA каждого файла.
- Контейнер видит стабильные пути: исходники `/workspace` только для чтения,
  эталон `/seed` только для чтения, рабочую сборку `/build` в своём tmpfs.
- В рабочую сборку копируются файлы с сохранением времени; изменённые исходники
  и заголовки получают время новее всех исходных артефактов. Поэтому Ninja
  пересобирает изменённые файлы и зависящие от них цели, а не использует старый
  бинарник. Изменение заголовка может закономерно вызвать большую пересборку.
- После линковки запускаются **новые тесты**. Никакое состояние рабочей копии
  попытки не публикуется в эталон.
- Изоляция CPU, памяти, PID, сети, capabilities, read-only rootfs и времени
  сохраняется. `/tmp` остаётся noexec, а `/build` явно exec для запуска тестов.
- Контейнер записывает CID; при отмене/таймауте runner дополнительно принудительно
  удаляет именно этот контейнер, а не только завершает клиент runtime.

При повреждении, устаревании, недоступности или неподдерживаемом содержимом
снимка используется холодная сборка. Ошибка инфраструктуры не считается
неправильным ответом. Быстрый зачёт точного совпадения с проверенным оригиналом
сохраняется; проверенные снимки переживают перезапуск runner.

## GoogleTest и кэши

Образ содержит Ninja и готовые Debian-библиотеки GoogleTest/GoogleMock.
Для стандартного `FetchContent(googletest)` runner подставляет локальный
адаптер: доступны `GTest::gtest`, `GTest::gtest_main`, `gtest`, `gtest_main`
и соответствующие gmock targets. Загрузка из сети в sandbox не требуется.
Также доступны source/include пути для обычных проектов.

Проекты с напрямую встроенной собственной версией GoogleTest могут собрать
её при подготовке; такие объекты сохраняются в снимке. Нестандартные зависимости
от внутренних исходников другой версии GoogleTest требуют проверки совместимости:
адаптер не обещает совместимости с любой частной модификацией библиотеки.

Постоянный ccache доступен только сборке оригинала, в новом namespace.
Студенческие сборки и тесты **не монтируют его**; сохранённый CMake compiler
launcher запускается с `CCACHE_DISABLE=1`. Иначе код мог бы сохранять состояние
или отравить будущие компиляции через общий изменяемый каталог.

Снимки хранятся в приватном каталоге runner, по умолчанию
`$HOME/build-snapshots`; в production это `/var/lib/cppdefense-runner/build-snapshots`.
Кэш управляет только собственными digest-каталогами. Непустой каталог без
маркера владения не принимается. Снимки блокируются межпроцессным flock и
публикуются атомарно.

Настройки:

```dotenv
CPPDEFENSE_BUILD_CACHE_DIR=/var/lib/cppdefense-runner/build-snapshots
CPPDEFENSE_BUILD_CACHE_MIB=2048
CPPDEFENSE_BUILD_CACHE_TTL=24h
CPPDEFENSE_RUNNER_SLOTS=1
```

Очистка удаляет старые неиспользуемые снимки; ограничение учитывает содержимое,
метаданные и оценку файловых накладных расходов, также действует предел 64 записей.
Текущие/заблокированные снимки и рабочие staging-копии могут временно превышать
лимит. На один экспорт отведено до 768 МиБ данных и 100000 файлов. Зависшие
после аварии staging-каталоги удаляются позднее под блокировкой.
Для VPS 2 vCPU/4 ГБ разумный начальный параллелизм — одна проверка.

## Очередь

Runner отправляет `wait_ms=10000` при получении задания. Backend сначала
подписывается на PostgreSQL LISTEN, затем проверяет очередь — между проверкой
и подпиской нет окна потери уведомления. INSERT/UPDATE задания вызывает NOTIFY
после commit. Раз в секунду проверяются отложенные задания и истёкшие lease.

Для ожидания используется отдельное соединение, не занятый connection из
обычного API pool. Нужно предусмотреть до одного дополнительного соединения
PostgreSQL на свободный runner slot. HTTP write timeout должен превышать
интервал ожидания; штатный timeout 30 секунд подходит.
Старый runner может продолжать немедленный polling. Новый runner умеет
откатиться на старый протокол при обновлении/откате backend; задержка polling
применяется только для legacy-режима и повторов после ошибок.

## Замеры

В API попытки сохраняется `timings`, в защите — `preparation_timings`.
В интерфейсе студента и в истории преподавателя есть раскрываемый блок
«Время проверки»: очередь, получение/распаковка, материализация, запуск
контейнеров, CMake, компиляция, линковка, сборка, копирование снимка и CTest.

Все значения — миллисекунды. Общее время включает очередь. Компиляция и
линковка измеряются launcher-обёртками; это сумма времени отдельных команд,
которые могут выполняться параллельно. Их нельзя складывать со временем сборки
как независимые последовательные интервалы. Нет замера — null, а не фиктивный
ноль. Замеры не используются для выставления вердикта или лимитов безопасности.
Для повторно использованного этапа явно показывается «Из проверенного снимка».

## Проверка и развёртывание

Обычный GitHub deploy обновляет backend, Go runner и образ sandbox. Установщик
копирует timing/GTest helpers в build context. Применяются миграции 000015/000016.
Новых секретов не требуется. Действующий VPS вручную не изменялся.

Добавлен отдельный CI workflow с настоящими Linux-контейнерами, не имитацией
сборки. Локальный запуск:

```bash
docker build -f deploy/sandbox.Dockerfile -t cppdefense-sandbox:test deploy
CPPDEFENSE_TEST_SANDBOX_IMAGE=cppdefense-sandbox:test \
CPPDEFENSE_TEST_CONTAINER_RUNTIME=docker \
go -C backend test -race ./internal/runner -run TestRealSandboxIncrementalSnapshotIsolation -count=1 -v
```

Тест проверяет оба режима защиты, неверные и альтернативные правильные ответы,
пересборку заголовков, повторный запуск, readonly seed, отсутствие общего ccache
у тестов и невозможность перенести изменённый `build.ninja` или marker теста
в следующую попытку. Отдельные тесты проверяют обход путей, quota, контроль
целостности, блокировки, очистку, уведомления PostgreSQL, API и отображение.

На маленьком фиксированном проекте с реальным GoogleTest в Docker Desktop
получено около 450 мс холодной сборки против 45 мс повторной сборки и 3 против
1 вызова компилятора. Это **только этап сборки тестового проекта**, не обещание
полного времени ответа на реальных лабораторных. Production rootless Podman
на VPS здесь не запускался.
