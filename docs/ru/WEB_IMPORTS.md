# Импорт групп и лабораторных в веб-версии

## Состав групп

Преподаватель загружает JSON, проверяет предварительный список изменений и
только затем подтверждает импорт. Все изменения применяются одной транзакцией.
Повторная загрузка обновляет ФИО и группу существующей записи по
GitHub-логину, не создавая дубликат.

```json
{
  "schema_version": 1,
  "organization": {
    "github_login": "is-itmo-c-26",
    "name": "ИС-26"
  },
  "groups": [
    {
      "code": "26-013",
      "name": "26-013",
      "students": [
        {
          "full_name": "Иванов Иван Иванович",
          "github_login": "ivanov"
        }
      ]
    }
  ]
}
```

## ZIP студента

Студент загружает обычный ZIP проекта без `cppdefense-manifest.json`. Имя
файла имеет вид `labwork1-USERNAME-deadline_0.zip`, где `USERNAME` должен
совпадать с GitHub-логином текущего аккаунта. Код группы берётся из привязанной
записи студента. Корень проекта может находиться непосредственно в ZIP или в
единственной верхней папке, как в архиве GitHub.

Система проверяет пути, лимиты архива, наличие корневого `CMakeLists.txt` и
C/C++ исходников, создаёт внутренний manifest и отправляет версию на проверку
преподавателю. До подтверждения версия не появляется в списке доступных защит.

## Импорт преподавателем через локальный git clone

Группы существуют только внутри CppDefense. Каждая группа хранит ссылку на
общую GitHub-организацию из roster JSON, а ожидаемое имя репозитория строится
как `<организация>/<код-лабы>-<github-login>`, например
`is-itmo-c-26/labwork1-ivanov`.

На компьютере преподавателя нужны Git, Python 3 и настроенная авторизация Git
по HTTPS (например, через менеджер учётных данных). В форме выберите группу,
нескольких студентов и лабораторные, укажите `deadline_N` и нажмите
«Подготовить команду». Скопируйте одну команду и выполните в терминале.
Она загружает скрипт с вашего сайта; тот клонирует репозитории, экспортирует
точный SHA через `git archive` и автоматически отправляет ZIP в CppDefense.
Выбирать файлы или загружать JSON вручную не требуется.

Кнопка «Вся группа · выбранные лабы · последний deadline» выбирает всех
студентов группы и формирует такой же пакет по выбранным лабораторным.
Скрипт получает `git ls-remote --heads` для каждого репозитория отдельно и
сравнивает номера численно: `deadline_10` новее `deadline_9`. Если deadline-веток
нет, ошибка показывается для этой работы, остальные продолжают импортироваться.

Разрешение подписано сервером, ограничено выбранными работами и действует
2 часа (не более 200 работ за пакет). Оно не даёт права подтверждать версии.
Повторный запуск одной команды не создаёт повторный импорт для уже загруженных
позиций: миграция 000012 хранит квитанции загрузки. Новая команда создаёт новый
пакет. При истечении срока создайте новую команду, выбрав оставшиеся работы.
ZIP появляются в очереди подтверждения; пока страница открыта, очередь
обновляется автоматически. Учётные данные GitHub на сайт не отправляются.

Backend не доверяет присланным метаданным: он повторно сверяет организацию,
группу, лабораторную и GitHub-логин со своей базой, нормализует ZIP и помещает
его в обычную очередь подтверждения преподавателем. SHA — метаданные экспорта:
сервер без GitHub-доступа не может независимо доказать соответствие содержимого
архива коммиту. Преподаватель проверяет и подтверждает загрузку.

## Кеш повторных сборок

Актуальный механизм — [проверенные снимки Ninja](INCREMENTAL_BUILDS.md).
Попытки получают отдельную копию сборки и не изменяют постоянный ccache.
Описанный ниже ccache применяется только при подготовке оригинала.

В production с Podman runner хранит `ccache` в отдельном именованном томе для
каждой сессии защиты и образа. Неизменившиеся единицы компиляции, включая
GoogleTest, повторно используются; CMake, линковка и CTest запускаются при
каждой попытке. Результаты тестов не кешируются. Лимит кеша — 256 МБ на сессию.
При недоступности создания тома используется обычная сборка; Docker runtime
пока работает без постоянного кеша. Новому runner нужен пересобранный образ
из `deploy/sandbox.Dockerfile` с установленным ccache (обычный production deploy
это делает). Время ускорения зависит от проекта; первая сборка прогревает кеш.
В журнал сборки добавляется статистика ccache: Hits показывают повторное
использование результатов компиляции.

После завершения защит можно освободить неиспользуемые кеши от имени пользователя
runner: `podman volume prune --filter label=cppdefense.cache=compiler`.
Это удаляет кеши не подключённых сейчас сессий, поэтому следующие попытки
потребуют холодной сборки. Данные PostgreSQL и MinIO этим фильтром не затрагиваются.

## GoogleTest

Проверка выполняется без сети в `cppdefense-sandbox`. Образ содержит CMake,
CTest, GCC и системный GoogleTest. Рекомендуемый CMake-код лаборатории:

```cmake
find_package(GTest REQUIRED)
add_executable(lab_tests tests.cpp)
target_link_libraries(lab_tests PRIVATE GTest::gtest_main)
include(GoogleTest)
gtest_discover_tests(lab_tests)
```

Старые проекты с `FetchContent_Declare(googletest ...)` также используют
локальный `/usr/src/googletest`: runner передаёт
`FETCHCONTENT_SOURCE_DIR_GOOGLETEST` и запрещает сетевую загрузку зависимостей.
Стандартная последовательность проверки — configure, build и
`ctest --output-on-failure`.

При production-деплое `deploy/install-runner-release.sh` пересобирает sandbox
из `deploy/sandbox.Dockerfile`, затем устанавливает новые runner/worker и
перезапускает службу. Поэтому отдельная установка GoogleTest в Ubuntu VPS не
нужна.

После первого обновления этого защищённого root-скрипта его нужно один раз
переустановить на VPS вручную:

```bash
cd /opt/cppdefense/source
sudo install -o root -g root -m 0755 \
  deploy/install-runner-release.sh \
  /usr/local/sbin/cppdefense-install-runner
```

Обычный деплой проверяет точное совпадение установленной копии и останавливается
до изменения приложения, если администратор ещё не выполнил этот шаг. Так
пользователь `cppadmin` не получает возможность незаметно подменить скрипт,
исполняемый от `root`.
