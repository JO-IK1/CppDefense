# ADR-0001: архитектура системы и структура репозитория

- **Статус:** принято
- **Дата:** 2026-09-12
- **Основание:** `docs/REQUIREMENTS_2.0.md`, версия 1.4

## Контекст

CppDefense 2.0 объединяет существующее C++-ядро, Go Backend, серверный frontend, PostgreSQL, S3-совместимое файловое хранилище, очередь и отдельный runner для недоверенных C++-проектов. Проект разрабатывает небольшая команда, а изменения протокола worker почти всегда требуют согласованных изменений C++ и Go.

## Решение

Использовать один публичный модульный monorepo с проприетарной source-available лицензией. Компоненты собираются отдельно, не импортируют внутренности друг друга и взаимодействуют только через зафиксированные контракты.

Рекомендуемая структура целевого репозитория:

```text
cpp-defense/
├── apps/
│   ├── api/                    # Go Backend и composition root
│   └── runner/                 # Go Runner Agent
├── internal/                   # закрытые Go-пакеты по слоям
│   ├── domain/
│   ├── application/
│   ├── transport/
│   └── infrastructure/
├── web/
│   ├── templates/              # Go templates
│   └── static/                 # HTMX, CSS, editor assets
├── cpp/
│   ├── apps/
│   │   ├── cli/
│   │   └── worker/
│   ├── include/cpp_defense/
│   ├── src/
│   └── tests/
├── contracts/
│   ├── manifests/
│   ├── worker/
│   └── openapi/
├── db/migrations/
├── deploy/
│   ├── vm-app/
│   ├── vm-runner/
│   └── backup/
├── docs/
│   ├── adr/

├── LICENSE

```

## Границы компонентов

### `cpp-defense-core`

- Чистые C++23 структуры и правила поиска/выбора функции.
- Не зависит от CLI, JSON, сети, PostgreSQL, MinIO или веба.
- Не запускает сборку и не управляет контейнерами.

### `cpp-defense` CLI

- Сохраняет сценарий v1 для локального запуска.
- Использует только публичный API core и локальные infrastructure-адаптеры.
- Не является production runner.

### `cpp-defense-worker`

- Headless-процесс с JSON через stdin/stdout.
- Выполняет только команды, описанные в `contracts/worker/v1`.
- Работает внутри выделенного workspace VM №2 и не принимает абсолютные пути.
- Не имеет сетевого доступа и не знает PostgreSQL/MinIO credentials.

### Go Backend

- Единственный владелец доменных записей PostgreSQL.
- Реализует GitHub OAuth, Telegram OIDC, серверные сессии, RBAC, импорт, защиты, очередь и audit.
- Выдаёт HTML и `/api/v1` из одной application-модели.
- Не запускает недоверенный код и не вызывает Docker Engine.

### Go Runner Agent

- Получает задания через отдельный аутентифицированный runner API.
- Не подключается напрямую к PostgreSQL.
- Получает архивы и отдаёт результаты через короткоживущие scoped URL/API.
- Управляет `cpp-defense-worker` и контейнерным runtime только на VM №2.
- Один job исполняется только владельцем актуального lease token.

### PostgreSQL

- Источник истины для пользователей, ролей, групп, лабораторных, импортов, защит, попыток, очереди и аудита.
- Бинарные ZIP и большие логи в таблицах не хранятся.

### `FileStorage`

- Application-порт с операциями put/get/head/delete и выдачей короткоживущего доступа.
- Первая production-реализация использует S3 API и MinIO.
- Object key непрозрачен и не содержит персональные данные.
- Код Backend не зависит от MinIO-specific API, чтобы заменить сервер без миграции домена.

### Frontend

- Go templates + HTMX; JavaScript используется только для редактора, таймера и live-статусов.
- Скрытие кнопки не считается проверкой доступа: каждый запрос проходит Backend policy.

## Размещение

```text
Интернет
   │
Cloudflare Tunnel
   │
VM №1: Backend/frontend ── PostgreSQL
   │                    └── S3/MinIO
   │ аутентифицированный runner API + scoped objects
   ▼
VM №2: Runner Agent ── контейнер проверки ── cpp-defense-worker
```

- Только Tunnel публикует VM №1 наружу.
- VM №2 инициирует соединение к VM №1; входящий пользовательский доступ к VM №2 отсутствует.
- Контейнер проверки не имеет сети и доступа к Docker socket, хостовым каталогам или соседним job.

## Правила зависимостей

1. Domain не зависит от transport/infrastructure.
2. Application зависит от domain и портов, но не от конкретной БД/S3/HTTP-библиотеки.
3. Infrastructure реализует порты application.
4. Transport переводит HTTP/JSON в application-команды.
5. Go не включает C++ как in-process библиотеку; связь только через worker JSON.
6. Runner не обновляет доменные таблицы напрямую.
7. Контракты версионируются до изменения реализаций.

## Версионирование и выпуск

- Продукт имеет общий SemVer release tag, например `v2.0.0-beta.1`.
- Worker protocol имеет независимую major/minor версию `1.0`.
- ZIP manifest имеет целочисленную `schema_version`.
- API использует URL-major `/api/v1` и OpenAPI `info.version`.
- Container images публикуются с release tag и immutable digest.
- Несовместимое изменение контракта требует новой major-версии контракта и периода совместимости.

## Репозиторий и лицензия

- Репозиторий публичен для просмотра как портфолио.
- Код не является open source; MIT/Apache/GPL-лицензия на собственный код не применяется.
- Корневые `LICENSE`, `README` и `SECURITY.md` обязательны.
- Реальные данные студентов, secrets, backups и production `.env` запрещены в любой Git-ветке и истории.

## Последствия

Плюсы:

- атомарные изменения C++/Go/схем;
- единый CI и release tag;
- проще воспроизводить совместимые сборки;
- меньше риска рассинхронизации протокола.

Минусы:

- CI должен уметь выборочно собирать C++ и Go;
- права Git нельзя разделить по компонентам;
- репозиторий крупнее.

## Отклонённые варианты

- **Несколько репозиториев:** увеличивает риск несовместимых версий и требует отдельного release orchestration.
- **C++ как библиотека внутри Go через C ABI/cgo:** усложняет изоляцию, сборку и обработку аварий.
- **Запуск Docker из Backend:** нарушает границу доверия между сайтом и недоверенным кодом.
- **Отдельный брокер очереди:** для 100 пользователей PostgreSQL-очередь проще и достаточно надёжна.

## Критерии пересмотра

ADR пересматривается, если появляются независимые команды, внешние клиенты worker/API, необходимость раздельных циклов релиза либо нагрузка, при которой PostgreSQL-очередь перестаёт выполнять SLO.
