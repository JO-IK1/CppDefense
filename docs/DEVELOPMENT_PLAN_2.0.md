**Дата создания:** 2026-09-07

**Целевой стек:** C++23, Go, PostgreSQL, MinIO, Go templates + HTMX, Linux containers, Cloudflare Tunnel

## 1. Цель плана

Довести существующее консольное C++-приложение до веб-системы, в которой преподаватель импортирует работы и проверяет архивы, GitHub подтверждает личность студента, система автоматически связывает однозначные записи, преподаватель разрешает конфликты, а отдельный runner безопасно собирает проект и запускает CTest.

Главные ограничения:

- до 100 активных пользователей;
- 4–6 параллельных проверок;
- приложение и проверки работают в разных Linux VM;
- PostgreSQL и MinIO переживают перезапуск и выключение ноутбука;
- полный исходный код публичен как портфолио, но лицензия проприетарная source-available;
- GitHub OAuth — основной способ регистрации и входа; Telegram OIDC — альтернативный;
- исходники студентов и результаты никогда не становятся публичными.

- student A не читает объекты student B;
- teacher группы A не читает группу B;
- блокировка отзывает активные сессии;
- повторная привязка отклоняется и журналируется.

### Готово, когда

- сценарий H требований проходит end-to-end;
- матрица ролей покрыта отрицательными тестами;
- полный student-сценарий через GitHub не обращается к Telegram;

### 17.1 Версия 2.1 — тестовая защита

Цель — дать студенту возможность безопасно потренироваться на собственной загруженной лабораторной до официальной защиты.

#### Доменная модель

- Добавить `defense_mode`: `official` или `practice`.
- Результат practice-защиты никогда не меняет официальный результат, балл или число официальных попыток.
- Teacher отдельно включает practice-режим для лабораторной и задаёт лимит времени, число запусков и период доступности.
- Practice использует отдельный `session_id`, seed и историю; выбранная функция не влияет на будущий официальный выбор.
- Все экраны, логи и выгрузки явно помечают тренировочный режим.

#### Очередь и ограничения

- Ввести приоритеты: официальная защита и контестная оценка выше practice.
- Ограничить число незавершённых practice-проверок на пользователя и частоту запусков.
- Разрешить admin временно отключить practice при высокой нагрузке.
- Хранить тренировочные логи отдельно и разрешить более короткий срок их хранения.

#### Интерфейс

- На карточке лабораторной показывать отдельную кнопку «Тестовая защита».
- До старта объяснять, что результат не влияет на оценку.
- Историю practice не смешивать с официальными защитами, но разрешить student и teacher просматривать её отдельной вкладкой.

#### Готово, когда

- студент может пройти полный тренировочный цикл CMake → Build → CTest;
- тренировочная попытка не изменяет официальный результат и балл;
- practice не вытесняет официальные задания из очереди;
- переключение параметра запроса не позволяет выдать practice за official.

### 17.2 Версия 2.2 — контесты и самостоятельная сдача лабораторных

Цель — перенести приём лабораторных на сайт: студент записывается на контест, загружает работу и получает автоматический балл после проверки.

#### Сущности и состояния

- Добавить `contest`, `contest_participant`, `contest_lab`, `student_submission`, `score_rule` и неизменяемый `score_event`.
- Contest содержит название, группу, преподавателей, время начала/окончания, разрешённые лабораторные, лимиты попыток и версию правил оценки.
- Состояния contest: `draft` → `registration_open` → `running` → `grading` → `closed` → `archived`.
- Участие создаётся явной записью student на contest; teacher/admin может добавить или исключить участника с причиной и audit.
- Загружать работу может только active student, записанный на открытый contest своей группы.

#### Сценарий студента

1. Student входит через GitHub и открывает доступный contest.
2. Подтверждает запись и видит сроки, правила, лимиты, доступные лабораторные и формулу балла.
3. Загружает ZIP одной лабораторной через сайт.
4. Backend выполняет ту же безопасную валидацию ZIP, что и для импорта teacher.
5. После успешной валидации создаётся неизменяемая `submission_version` с источником `student_upload`.
6. Проверка немедленно ставится в приоритетную очередь и выполняет CMake → Build → CTest в sandbox.
7. После завершения система рассчитывает балл, сохраняет `score_event` и сразу показывает student итог и безопасный лог.

#### Автоматическая оценка

- Формула оценки задаётся teacher до открытия contest и после первой сдачи не меняется; исправление создаёт новую версию правила.
- Базовые входы формулы: configure, build, число пройденных CTest, обязательные тесты, время отправки, номер попытки и штраф за опоздание.
- Для MVP результат определяется автоматически: не собралось — 0; собралось, но тесты пройдены частично — пропорциональная часть; все обязательные тесты пройдены — полный балл с применением настроенных штрафов.
- Точный балл считается только на Backend по сохранённой версии правила; frontend не присылает готовое значение.
- Повторная доставка результата job не создаёт второй балл благодаря idempotency key.
- Технический результат попытки неизменяем. Teacher/admin может оформить отдельную ручную корректировку с причиной; исходный автоматический балл остаётся в истории.
- Для нескольких попыток contest явно задаёт правило итогового балла: `best`, `last` или `first_passed`; рекомендуемое значение по умолчанию — `best`.
- Скрытые тесты и их исходный код student не получает; видимая часть лога настраивается teacher.

#### Безопасность и честность

- Student upload проходит лимиты ZIP Slip/ZIP bomb и никогда не запускается на VM приложения.
- Для загрузки и повторных попыток действуют rate limits и contest-лимиты.
- Deadline считается на сервере; принятая до срока работа оценивается, даже если ждала runner после deadline.
- SHA-256 архива, версия sandbox image, компилятора, тестов и score rule сохраняются вместе с результатом.
- После закрытия contest новые загрузки запрещены; teacher может открыть индивидуальное исключение только с причиной и audit.

#### Интерфейс teacher/admin

- Создание contest из шаблона или с нуля.
- Управление записью участников и проблемами сопоставления GitHub.
- Таблица live-статусов: не сдавал, в очереди, проверяется, ошибка, оценено.
- Ведомость с текущим итоговым баллом и историей всех score events.
- CSV-экспорт ведомости без исходников и секретных тестов.
- Повторная проверка после исправления инфраструктуры без создания новой student attempt или штрафа.

#### Готово, когда

- записанный student загружает лабораторную и получает балл без ручной операции teacher;
- незаписанный student и участник другой группы не могут загрузить работу;
- одинаковый результат job не выставляет балл дважды;
- формула и её версия позволяют воспроизвести любой выставленный балл;
- teacher видит ведомость и может объяснить состав балла;
- контестная нагрузка не нарушает официальные защиты.

### 17.3 Версия 3.0 — постоянно работающий сервис

Домашний Windows-ноутбук подходит для 2.0 и демонстраций, но не считается надёжной площадкой 24/7. До запуска регулярных контестов приложение переносится на постоянно включённый сервер/VPS либо отдельный домашний сервер с гарантированным питанием и резервным интернетом. Рабочий ноутбук не должен оставаться единственной точкой отказа.

#### Инфраструктура

- Перенести Backend, PostgreSQL и MinIO на постоянный хост; runner допускается масштабировать отдельными машинами через исходящие аутентифицированные соединения.
- Сохранить изоляцию приложения и runner; пользовательский код не выполняется на хосте Backend.
- Настроить автоматический restart, обновления с миграциями, maintenance mode и документированный rollback.
- Организовать минимум две независимые резервные копии, одна из которых находится у другого провайдера/на другой площадке.
- Ужесточить цели до RPO не более 1 часа для PostgreSQL и RTO не более 1 часа для пользовательского сайта.
- Добавить внешний uptime-monitoring, алерты владельцу и публичную страницу состояния или понятное сообщение о технических работах.
- Измерить пиковую нагрузку регистрации, массовой загрузки перед deadline и одновременного получения оценок.

#### Очередь

- Поддержать отдельные классы приоритета: `official_defense`, `contest_grading`, `teacher_recheck`, `practice`.
- Гарантировать минимальную квоту runner для official/contest, чтобы practice не создавал starvation.
- Автоматически масштабировать число runner либо отключать новые practice-задачи при превышении порогов очереди.

#### Эксплуатация

- Назначить владельца инцидента и каналы оповещения.
- Ввести расписание резервных копий, восстановления, обновлений и ротации секретов.
- Публиковать правила хранения студенческих работ и результатов, сроки удаления и контакты для обращения.
- Перед каждым contest выполнять readiness-check домена, GitHub OAuth, PostgreSQL, MinIO, runner и свободного места.

#### Готово, когда

- сервис проходит длительный soak-тест и доступен вне домашней сети;
- потеря одного runner не останавливает сайт и не теряет принятые сдачи;
- восстановление из внешней копии укладывается в RPO/RTO;
- массовая отправка перед deadline не создаёт двойных баллов и не теряет задания;
- владелец получает оповещение о недоступности раньше, чем обращение пользователя.
